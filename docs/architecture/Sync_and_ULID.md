# Syncing and ULID Block IDs

**Status:** Accepted -- included in v2 format

This document captures the accepted design for replication/sync capabilities in EmailDB and the change of `BlockId` from `long` to ULID. Rationale and alternatives are retained for historical context.

---

## 1. Motivation

EmailDB's append-only block storage model is a natural fit for replication. EmailContent blocks are immutable - they are never overwritten, never re-encrypted, and never removed by compaction. This means syncing can be reduced to "copy blocks the other side doesn't have."

The current `BlockId` (a `long` with range-based type encoding) provides uniqueness but no temporal ordering. A ULID-based BlockId would give us both uniqueness and lexicographic time ordering, making it trivial to compute sync deltas: "give me everything after ULID X."

---

## 2. Current Block Identity Model (v1 -- deprecated)

> **Note:** The v1 range-based `long` identity scheme described below is deprecated. v2 replaces it entirely with ULID BlockIds. `BlockType` in the block header is the authoritative source for a block's type; range-based type inference is removed.

BlockIds were previously 8-byte `long` values, generated by `BlockIdGenerator` using reserved ranges per type:

| Range Start | Block Type |
|---|---|
| 0-3 | System blocks (Header, Metadata, FolderTree, WAL) |
| 1,000,000,000,000 | Folders |
| 2,000,000,000,000 | Segments |
| 3,000,000,000,000 | Cleanup |
| 4,000,000,000,000 | Custom |
| 5,000,000,000,000 | BTree Leaf |
| 6,000,000,000,000 | BTree Internal |
| 7,000,000,000,000 | IndexRoot |
| 8,000,000,000,000 | EmailContent |

This encoding let you infer the block type from the ID alone, which was convenient for debugging. However, it provided no temporal ordering - you could not determine which block was written first by comparing IDs.

---

## 3. ULID Block IDs (Accepted Design)

### What is a ULID?

A ULID (Universally Unique Lexicographically Sortable Identifier) is a 128-bit (16 byte) identifier that encodes:
- 48-bit millisecond timestamp (high bits)
- 80-bit cryptographic randomness (low bits)

Because the timestamp occupies the high bits, ULIDs sort lexicographically in creation order. Multiple ULIDs generated within the same millisecond are guaranteed monotonically increasing (the random component is incremented).

### Design

ULID BlockIds are 16 bytes, stored directly in the block header. The range-based type inference used by v1 is removed entirely -- `BlockType` in the block header is the authoritative source for a block's type.

### Why ULIDs for BlockId?

1. **Temporal ordering for free.** A ULID *is* your block sequence number. No need for a separate monotonic counter.
2. **Sync high-water mark.** Backup says "give me everything after ULID X." Active responds with all blocks having a greater ULID. Delta computation is a single comparison.
3. **Multi-replica uniqueness.** Two replicas generating ULIDs simultaneously produce globally unique IDs with no coordination. No range partitioning needed.
4. **Deterministic sort order within a millisecond.** The spec guarantees monotonicity, so blocks written in rapid succession on the same node are strictly ordered.

### What We Lose

- **Range-based type inference.** You can no longer determine a block's type from its ID. `BlockType` is already stored in the block header, so this is a debugging/logging convenience loss, not a structural one.

## 4. Sync Models

### 4.1 Active to Backup (v1 scope)

The only sync model in scope for v1. One node accepts all writes; the backup is a read-only follower.

#### Email content sync

The backup tracks a ULID high-water mark: the ULID of the last EmailContent block it received. On each sync cycle:

1. Backup asks active: "give me all EmailContent blocks with ULID > X."
2. Active streams the delta blocks.
3. Backup appends them to its own file and advances its high-water mark.

#### Folder structure sync

Each folder has a `FolderVersion: ulong` counter stored on the FolderContent block. This counter increments every time the delta log compiles into the folder chain blocks.

Sync procedure:

1. Backup compares its `FolderVersion` per folder against the active's advertised versions.
2. For any folder where the backup is behind, it receives the current folder chain blocks wholesale from the active.
3. No delta log retention is required for sync purposes. Delta logs are local-only and exist solely for folder page maintenance.

#### KeyStore sync ordering

Unchanged from the original proposal. If new blocks use a new encryption epoch, the KeyStore block must be sent before (or atomically with) the EmailContent blocks that depend on it. Otherwise the backup cannot decrypt them.

### 4.2 Active to Active (out of scope for v1)

Active-to-active sync is **out of scope for v1**. The recommended pattern for multi-machine operation is:

- **One machine (Active1) is authoritative** for all mutable structures: folder membership, flags, BTree indexes.
- **A second machine (Active2) submits mutations** via an **application-layer actions channel** -- Add/Delete/Move/FlagChange RPCs sent to Active1.
- **Active1 applies the mutations locally**, and the results replicate back to Active2 through the normal Active-to-Backup replication channel described in 4.1.
- **Active2 never has its own divergent folder state** -- it is a client with a local read replica.
- **The actions channel is transport-agnostic** (HTTP, gRPC, message queue) and is **not** part of the storage format specification.
- **This eliminates all merge conflicts:** Active1 is the single writer for folder structure.
- **EmailContent blocks remain conflict-free** -- same content produces the same `EmailHashedID`, so inserts are idempotent and can be shipped from either direction.

## 5. BTree Impact of ULID Change

### Leaf Nodes

BTree leaf entries store `(EmailHashedID, BlockId)`. The accepted design removes `BlockOffset` from BTree leaves; offsets are resolved at runtime via `Dictionary<Ulid, long>`.

| Field | v1 (deprecated) | v2 (accepted) |
|---|---|---|
| Key (EmailHashedID) | 32 bytes | 32 bytes (unchanged) |
| BlockOffset | 8 bytes | -- (removed) |
| BlockId | 8 bytes | 16 bytes (ULID) |
| **Total per entry** | **48 bytes** | **48 bytes** |

Same entry size, same leaf density. With 4036 byte max payload and 69 byte node header (3967 usable bytes):

- **v1:** 3967 / 48 = **82 entries per leaf**, min underflow = 41
- **v2:** 3967 / 48 = **82 entries per leaf**, min underflow = 41

### Internal Nodes

**Unchanged.** Internal nodes store separator keys (EmailHashedID), child offsets, and child hashes. No BlockIds are stored in internal nodes.

### Tree Height

No change from v1. With 82 entries per leaf and 55 children per internal node:

| Email Count | Entries per Leaf | Capacity at Height |
|---|---|---|
| 10,000 | 82 | Height 2 (82 * 55 = 4,510) |
| 100,000 | 82 | Height 3 (248K capacity) |
| 1,000,000 | 82 | Height 4 (13.6M capacity) |
| 10,000,000 | 82 | Height 4 |

The ULID change does not increase tree height or reduce leaf density at any practical scale.

### WAL Entry Size

BTree WAL entries store `(Key, BlockId)` -- 32-byte EmailHashedID + 16-byte ULID = **48 bytes** per entry. Same as v1 (which stored 32-byte key + 8-byte offset + 8-byte BlockId). The auto-flush threshold remains at 82 entries to match leaf capacity.

---

## 6. BTree Offset Resolution

BTree leaf entries contain `BlockId` (ULID) as the durable pointer to each email content block. File offsets are **not** stored in the BTree. Instead, offsets are a runtime-only acceleration structure.

A `Dictionary<Ulid, long>` maps BlockId to the physical file offset. This dictionary is rebuilt on file open from the Checkpoint block (which records the block-id-to-offset mapping at the time of the last checkpoint), followed by an incremental scan of any blocks written after the checkpoint.

This cleanly separates durable identity (ULID, which is stable across replicas and compaction) from physical layout (file offset, which is local to a specific file). Syncing never needs to transfer or remap offsets -- each replica maintains its own offset dictionary from its own file layout.

---

## 7. Encryption Considerations for Sync

### Same Encryption Domain (Simpler)

Both replicas share the same password/key file and derive the same KEK. The KeyStore block (containing wrapped DEKs) can be synced directly. Both sides can decrypt any block using the same key material.

**Sync order matters:** If the active rotates keys (new epoch), the updated KeyStore block must arrive at the backup before any EmailContent blocks encrypted with the new epoch. Otherwise those blocks are temporarily unreadable.

### Separate Encryption Domains (Harder)

Each replica has its own password/KEK. Syncing encrypted blocks would require decrypt-on-source, re-encrypt-on-destination. This is significantly more complex and negates the advantage of shipping raw immutable blocks. Not recommended for V1.

### What Doesn't Change

- Blocks carry their `KeyEpoch` in a separated header field, so any replica with the appropriate DEK can decrypt any block regardless of which epoch it was written under.
- Email content blocks are never re-encrypted, even after key rotation. Old epochs remain valid for reading existing blocks.
- The KeyStore block itself is small (one entry per epoch) and cheap to sync.

## 8. Open Questions

1. **ULID library choice.** Still open but scoped. Need a .NET ULID implementation that guarantees monotonicity within the same millisecond and provides efficient 128-bit comparison. Options include `Ulid.NET` or a custom struct.

2. **Sync transport.** Still open. The protocol is transport-agnostic and could be implemented over TCP streams, HTTP chunked responses, or even file copy for offline sync. Sync transport is explicitly **out of scope for the format specification** -- the format defines the block layout and identity scheme, not the wire protocol.

3. **Sync log vs. tombstones vs. BTree diff.** **RESOLVED.** FolderDeltaLog is local-only (page maintenance). The `FolderVersion` counter drives sync freshness -- the backup compares its version per folder and receives full folder chain blocks when stale. No separate sync log, no tombstone block type, no BTree diffing required for sync.

4. **Compaction coordination.** If active compacts metadata/BTree blocks, the backup doesn't need to know (it maintains its own index). But if we ever compact EmailContent blocks (currently never), sync gets more complex. Should we explicitly guarantee EmailContent blocks are never compacted, as a contract?

5. **Format version bump.** **RESOLVED.** The v2 format bundles all breaking changes together: ULID BlockIds, separated KeyEpoch header field, Checkpoint blocks.

6. **Partial sync / resumption.** Checkpoint blocks provide the anchor point for sync state. If sync is interrupted mid-transfer, the ULID high-water mark should only advance after all blocks in a batch are confirmed written. The Checkpoint block records the last-known-good sync position.

---

## 9. Summary

| Aspect | Decision |
|---|---|
| ULID as BlockId | **Accepted.** 16-byte ULID replaces 8-byte `long`. Entry size unchanged at 48 bytes (offset removed, ULID fills the space). No leaf density or tree height impact. Gives temporal ordering and sync delta computation for free. |
| Active-to-Backup sync | **In scope (v1).** EmailContent blocks sync via ULID high-water mark. Folder structure syncs via `FolderVersion` counter with full folder chain block transfer when stale. KeyStore block syncs before new-epoch content. |
| Active-to-Active sync | **Out of scope (v1).** Recommended pattern: single authoritative writer (Active1), second machine submits mutations via application-layer actions channel, results replicate back through normal Active-to-Backup channel. |
| BTree offset resolution | **Decided.** BlockId (ULID) is the durable pointer. Offsets are runtime-only, stored in `Dictionary<Ulid, long>`, rebuilt on open from Checkpoint block + incremental scan. |
| Encryption | Same encryption domain is strongly preferred. KeyStore block must sync before new-epoch content blocks. KeyEpoch stored in separated header field. |
| Format impact | **v2 format.** ULID BlockIds, separated KeyEpoch field, and Checkpoint blocks are bundled into the v2 format change. |
